## User Scenarios & Testing *(mandatory)*

### User Story 1 - Save Class Recording (Priority: P1)

A trainer decides they want to record the current live session for students to review later. They click the "Record" button in their classroom dashboard. When the class ends, the recording is permanently saved and processed.

**Why this priority**: Core functionality for saving on-demand video for absent students.

**Independent Test**: Can be fully tested by starting a session, clicking "Record", ending the session, and verifying the video file remains in the storage bucket and triggers the transcode process.

**Acceptance Scenarios**:

1. **Given** a live classroom session, **When** the trainer clicks "Record", **Then** the UI indicates recording is active and the system flags the session to keep the recording.
2. **Given** a session flagged to keep the recording, **When** the trainer ends the session, **Then** the system retains the video file in the storage bucket and initiates post-processing (transcoding).

---

### User Story 2 - Discard Unwanted Recording (Priority: P1)

A trainer runs a private session, a quick test, or simply decides the current class shouldn't be recorded. They either never click "Record", or they click "Stop Recording" before the class ends. To save storage space, the system automatically deletes the background recording file when the session ends.

**Why this priority**: Critical for saving storage costs and respecting privacy when recordings are not explicitly requested.

**Independent Test**: Can be fully tested by starting a session, never clicking "Record" (or turning it off), ending the session, and verifying the video file is deleted from the storage bucket.

**Acceptance Scenarios**:

1. **Given** a live classroom session where recording is NOT enabled by the trainer, **When** the session ends, **Then** the system automatically deletes the corresponding video file from the storage bucket.
2. **Given** a live classroom session where the trainer clicked "Record" but then clicked "Stop Recording", **When** the session ends, **Then** the system deletes the video file from the storage bucket.

---

### Edge Cases

- What happens if the session crashes or ends abruptly without the trainer explicitly clicking "End Session"? (Will the cleanup script still run?)
- What happens if the storage bucket deletion API call fails? (Is there a retry mechanism or a lifecycle rule to clean up orphaned files?)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Trainer UI MUST display a toggleable "Record" button during a live session.
- **FR-002**: The system MUST track a `keep_recording` state for the active session, updating it when the trainer toggles the Record button.
- **FR-003**: The UI MUST clearly indicate to the trainer whether the session is currently set to be recorded or not.
- **FR-004**: When a session ends, the system MUST check the `keep_recording` state.
- **FR-005**: If `keep_recording` is true, the system MUST retain the background-recorded video file in storage and trigger the standard transcoding pipeline.
- **FR-006**: If `keep_recording` is false, the system MUST securely delete the temporary video file generated by the media server from the storage bucket.

### Key Entities 

- **Session**: Tracks the `keep_recording` boolean flag (or relies on a separate API call to persist the choice).
- **Storage Bucket**: The location where the video files are continuously saved by the media server, and from where they must be deleted if unwanted.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Trainers can successfully toggle the recording state within 1 second of clicking the button.
- **SC-002**: 100% of unwanted recordings (where `keep_recording` is false) are successfully deleted from the storage bucket upon session end.
- **SC-003**: 100% of requested recordings (where `keep_recording` is true) are retained and successfully sent to the transcoder upon session end.
- **SC-004**: Storage costs are measurably reduced by not retaining unwanted classroom recordings.

## Assumptions

- The backend system relies on the "Auto-Delete Strategy", where the media server continuously records to storage by default.
- The storage bucket credentials and endpoint are accessible by the backend service that handles the "End Session" logic.
- "Stop Recording" mid-session simply means the entire file will be discarded at the end, rather than attempting to slice the video file.
