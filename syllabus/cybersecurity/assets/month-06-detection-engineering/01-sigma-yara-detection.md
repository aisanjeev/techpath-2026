# Detection as Code — Sigma Rules & YARA

## Why Detection Engineering Matters

A SOC analyst who only responds to alerts generated by someone else's rules will always be reactive. Detection engineers write the rules — they decide what gets detected. This is the skill that separates L2/L3 from L1, commands higher pay, and is increasingly in demand as organisations build dedicated detection teams.

**Detection as Code** treats detection rules like software:
- Stored in version control (Git)
- Peer-reviewed before deployment
- Tested automatically against known-bad and known-good samples
- Deployed via CI/CD pipelines
- Monitored for efficacy over time

## Sigma — The Language of Detection

Sigma is a generic, vendor-neutral, YAML-based detection rule format. One Sigma rule can be converted to:
- Splunk SPL
- Microsoft Sentinel KQL
- Elastic Lucene
- OpenSearch
- QRadar
- And dozens more

### Anatomy of a Sigma Rule

```yaml
title: Suspicious Scheduled Task Creation
id: 56c217c3-2de2-479b-990f-5c4278d4d1eb  # UUID — unique identifier
status: stable  # experimental | test | stable | deprecated
description: Detects creation of scheduled tasks via schtasks.exe with /create flag
author: Florian Roth
date: 2023/04/15
modified: 2024/01/10

logsource:               # Which log source does this target?
  category: process_creation
  product: windows

detection:
  selection:             # Define named detection patterns
    Image|endswith: '\schtasks.exe'
    CommandLine|contains:
      - '/create'
      - '-create'
  filter_legit:          # Named exclusion (false positive filter)
    ParentImage|contains:
      - '\System32\services.exe'
      - '\Windows Defender\'
  condition: selection and not filter_legit  # Combine with boolean logic

falsepositives:
  - Legitimate software installation
  - System administration tools
level: medium            # informational | low | medium | high | critical
tags:
  - attack.persistence
  - attack.t1053.005    # MITRE ATT&CK Technique ID
```

### Sigma Field Modifiers

| Modifier | Effect | Example |
|----------|--------|---------|
| `contains` | String is anywhere in field | `CommandLine\|contains: 'evil'` |
| `startswith` | String at start of field | `Image\|startswith: 'C:\\Windows'` |
| `endswith` | String at end of field | `Image\|endswith: '\\cmd.exe'` |
| `re` | Regular expression | `CommandLine\|re: '.*Invoke-\w+'` |
| `all` | ALL listed values must match | (applied to list) |
| `base64offset` | Base64-encoded in field | (for obfuscated commands) |

### Sigma Condition Logic

```yaml
# Fire if ANY of the selection* patterns match
condition: 1 of selection*

# Fire only when selection AND filter are BOTH present
condition: selection and filter

# Fire when selection matches but NOT the filter (exclude false positives)
condition: selection and not filter_legit

# Fire when any of multiple selections match
condition: selection_process or selection_network
```

### Converting Sigma Rules

```bash
# Install pySigma
pip install pySigma pySigma-backend-splunk pySigma-backend-microsoft365defender

# Convert to Splunk
sigma convert -t splunk -p ecs_windows my_rule.yml

# Convert to Microsoft Sentinel KQL
sigma convert -t microsoft365defender -p ecs_windows my_rule.yml
```

Online: https://sigconverter.io/ (no install needed)

## YARA — Pattern Matching for Malware

YARA describes patterns to identify malware families in files, memory, or network streams. It's used by VirusTotal, AV vendors, incident responders, and threat hunters.

### YARA Rule Structure

```yara
rule RansomwareGeneric
{
    meta:
        description = "Detects generic ransomware characteristics"
        author = "YourName"
        date = "2026-08-04"
        severity = "high"

    strings:
        // Text strings (case-insensitive)
        $ransom_msg1 = "Your files have been encrypted" nocase
        $ransom_msg2 = "bitcoin" nocase
        $ransom_msg3 = "decrypt" nocase

        // Hex strings (exact byte sequences)
        $mz_header = { 4D 5A }        // MZ header = Windows PE executable
        $pe_header = { 50 45 00 00 }  // PE signature

        // Regular expressions
        $btc_address = /1[a-zA-Z0-9]{25,34}/

    condition:
        // MZ header present AND at least 2 string indicators
        $mz_header at 0 and 2 of ($ransom_msg*) or $btc_address
}
```

### YARA String Types

| Type | Syntax | Notes |
|------|--------|-------|
| Text | `$s = "string"` | Simple string match |
| Text (nocase) | `$s = "string" nocase` | Case-insensitive |
| Hex | `$h = { 4D 5A 90 00 }` | Exact byte match |
| Hex (wildcards) | `$h = { 4D ?? 90 }` | `??` = any byte |
| Regex | `$r = /pattern/` | PCRE-style regex |
| Wide string | `$w = "string" wide` | UTF-16 (Windows strings) |

### YARA Condition Operators

```yara
condition:
    all of them             // All strings must match
    any of them             // At least one string must match
    2 of ($str*)            // At least 2 of $str1, $str2, $str3 must match
    $str at 0               // $str must appear at offset 0 (file start)
    #str > 5                // $str must appear more than 5 times
    filesize < 2MB          // Only match files under 2MB
    uint16(0) == 0x5A4D     // MZ header check using integer comparison
```

### Running YARA

```bash
# Scan a single file
yara rule.yar suspicious_file.exe

# Scan a directory recursively
yara -r rules/ /path/to/scan/

# Scan running processes (memory)
yara -p 10 rule.yar $(pgrep -d, "suspicious_process")

# Verbose output with string matches
yara -s rule.yar file.exe
```

## The Detection Lifecycle

```
Write → Test → Tune → Deploy → Monitor → Review
```

### 1. Write
Start from threat intelligence, ATT&CK techniques, or observed attacker behaviour. Reference existing Sigma community rules for inspiration.

### 2. Test
- Test against **known-bad** samples — does it fire?
- Test against **known-good** traffic — does it stay silent?
- Use atomic-red-team tests: https://github.com/redcanaryco/atomic-red-team

### 3. Tune
Reduce false positives by adding filters for legitimate tools/paths. Track false positive rate — aim for < 5%.

### 4. Deploy
Convert to SIEM query syntax. Add to version control. Code review by another analyst. Deploy to staging first, then production.

### 5. Monitor
Track: alert volume, false positive rate, analyst closure rate, mean time to triage.

### 6. Review
Monthly review — is this still relevant? Did attackers change their TTP? Should the rule be updated or retired?

## Detection Efficacy — Key Metrics

| Metric | Target |
|--------|--------|
| False Positive Rate | < 5% of alerts per rule |
| Mean Time to Triage (MTTT) | < 10 minutes for P2 |
| Detection Coverage | % of MITRE ATT&CK techniques covered |
| Alert Volume | Stable — not growing unbounded |

**Alert fatigue is a detection failure.** If a rule generates too many FPs, analysts stop investigating it — and real threats hide in the noise.
